# LyricCar 歌词（lyriccar）

车机上全屏显示歌词的 Android App（Flutter 写的，横屏）。

**它不接管音频**：声音照旧由车机自带的蓝牙播放器出，本 App 只是坐在旁边看系统
媒体会话（MediaSession），把歌词一句句采集下来、存起来、显示出来。

**它不连外网**：歌词全靠本地听出来，一个网络请求都不发。唯一会用到网络的是
「局域网传输」—— 那时它在车上起一个很小的 HTTP 服务，让同一个 Wi-Fi 下的手机
连上来取歌词库（面板关掉就停，见下文）。

## 它解决什么问题

车机的蓝牙音乐界面只有三行：**标题 / 歌手 / 专辑**。想让屏幕上滚歌词，就得
「借」一行来写歌词 —— 播放器每换一句就更新一次媒体信息，车机看起来就是在滚动歌词。
网易云、QQ 音乐、哔哩音乐的「车载歌词 / 蓝牙歌词」都是这个原理。

借哪一行各家不一样，所以本 App **三行都支持，而且能自己认出来**：

| 借的那一行              | 谁这么干           | 代价                                   |
| ----------------------- | ------------------ | -------------------------------------- |
| **歌手行** / **专辑行** | 车机自带蓝牙播放器 | 无（歌名还在）                         |
| **歌曲名行**            | 网易云、QQ 音乐    | 歌名没了 —— 车机界面上那一行被歌词顶掉 |

这个 App 就是这套玩法的**接收端**：

```
播放器（网易云 / QQ 音乐 / 车机自带蓝牙播放器）
   把歌词写进 MediaMetadata 的 歌手行 / 专辑行 / 歌曲名行
        ↓  系统媒体会话（MediaSession）
本 App 读 MediaMetadata → 盯着那一行，变一次记一句 + 记下当时的播放位置
        ↓
歌词库（本地 JSON）→ 全屏同步滚动显示
```

于是：

- **第一遍听**：边听边攒歌词（界面上能看到已采集多少句）；
- **听到一半就切走 / 退出 App 也不要紧**：下次放这首歌，**不用等采完**就能按播放位置
  滚歌词 —— 采到的部分照滚，还没采到的部分边放边补，已经采过的句子不会被改乱；
- **一首放完**：整首歌词就齐了，标记为「完整」；
- **第二遍起**：直接从本地歌词库按播放位置同步显示，不用再采集；
- **换车机**：导出成一个 JSON 文件带过去导入；两台车在同一个 Wi-Fi 下时，
  也可以让新车机连老车机的地址直接拉过去。

## 用法

1. 装到车机上（横屏）。
2. 首次打开，按提示授予**通知使用权**：
   `设置 → 应用 → 特殊应用权限 → 通知使用权 → 勾选「LyricCar 歌词」`。
   这是 Android 允许普通 App 读取**别人**的媒体会话的唯一入口，不开这个只会一片空白。
3. 在播放器里打开「车载歌词 / 蓝牙歌词」（它负责把歌词写进媒体信息）。
4. 放一首歌：
   - 面板左侧能看到它从系统读到的**标题 / 歌手 / 专辑原值**和来源 App；
   - 右侧：第一次是「采集中」，放完之后下一次就是完整歌词同步滚动。

5. 点歌词任意一行可以跳转到那句（通过 MediaController 转发给播放器）。
6. 想换车机 / 备份时，进「歌词库」用「导出到下载」或「局域网传输」——
   第一次导出会问一次存储权限（Android 9 及以下），允许就行。

如果一直采不到歌词，去「设置 → 歌词写在」把「自动判断」换成「专辑行」试试 ——
不同播放器写的那一行不一样，没有统一标准。左侧面板把这两行的原始内容显示出来，
就是给这个排查用的。

## 歌词写在哪一行（自动判断）

设置里的「歌词写在」有四档：**自动判断（默认）/ 歌手行 / 专辑行 / 歌曲名行**。

正常情况下**不用动**这个设置。选「自动判断」时，本 App 靠一条硬信号自己认：

> **标题在变，但播放位置一直在往前走 → 标题被当成歌词在用了。**

理由很朴素：同一首歌里歌词一句接一句，位置只会一路向前（网易云实测每两三秒一句）；
而**真的换歌时，播放位置一定会从头开始**，不可能还往前走。所以要求「标题变了，
且位置比上一次至少前进了 0.5 秒」，光看到标题变了不算。

这样同一个车机上换着放不同的播放器也都能各自认出来：哔哩音乐（歌词在歌手行）
走的是「歌手行」那套，网易云（歌词在歌曲名行）会自动切到「歌曲名行」那套。
判断是**每首歌重新做一次**的，所以不会从一个播放器泄漏到另一个。

### 怎么在库里找到这首歌（两套，先按歌名）

| 顺序 | 用什么找 | 为什么 |
| --- | --- | --- |
| ① 先按**歌名** | 歌手行里的 `歌曲名 - 歌手` → 取前半段 | 歌名基本唯一，而且**不受时长抖动影响** |
| ② 找不到再按**换歌后那套 key** | 歌手行/专辑行模式：`标题 + 时长`（5 秒桶）<br>歌曲名行模式：`歌手 + 专辑 + 时长` | 兜住「重名」「歌手行不是那个格式」等情况 |

为什么先按歌名：那套 key 里带着播放器报的**时长**，同一首歌报 `3125` 和 `3120` 秒就会
变成两个 key，白采一遍（真机抓到过）。歌名不受这个影响 —— 但它会重名，所以还得有②。

歌词写在歌曲名行时，真歌名只能从**歌手行**拿：播放器会把身份信息挪过去，
格式是 `歌曲名 - 歌手`，实测长这样：

```
TITLE  = 当前这句歌词（每两三秒一变）
ARTIST = River Flows in You (在你身上流动的河) - Yiruma
ALBUM  = River Flows in You
```

所以**切歌那一瞬间就要把歌名抓住**：标题过一两秒就被歌词盖掉了。歌手行不带这个格式时，
退而求其次把「切歌后第一眼看到的标题」当真歌名（那一眼通常还是真歌名）。

名字匹配错了也能纠回来：名字对上之后，还要用**歌词本身**验一句 ——
这一句应该落在稿子里同一位置附近的那句上。连续两句对不上（或者同一句在稿子里差了
几十秒），就否定这次匹配，退回②再找一遍；②也没有就新开一份，**错的那份原样留着**。

⚠️ 歌手行如果是 `专辑 - 歌手`（而不是 `歌曲名 - 歌手`），切出来的「歌名」其实是专辑名，
同一张专辑里的几首歌会看起来同名 —— 所以匹配时**还要比时长**（差超过 20 秒就不算），
再加上上面那道歌词验证兜底。

## 导出 / 导入（三种）

歌词库面板右上角三个按钮：

| 按钮           | 干什么                                                                                |
| -------------- | ------------------------------------------------------------------------------------- |
| **导出到下载** | 把整个库存成一个 JSON，写进**系统「下载」目录**（`下载/LyricCar/lyriccar-时间.json`） |
| **从下载导入** | 列出下载目录里的 `.json`，挑一份导进来                                                |
| **局域网传输** | 车上起一个 HTTP 服务，手机连上去下载 / 上传（见下）                                   |

**为什么要自己写「下载」目录**：这台 BYD 车机（Android 9）没有能处理系统「另存为」
（SAF `ACTION_CREATE_DOCUMENT`）的 Activity ——

```bash
adb shell cmd package resolve-activity -a android.intent.action.CREATE_DOCUMENT
# → No activity found
```

所以走系统文件选择器**必然失败**（这正是之前「导出失败」的原因）。现在直接写公共
下载目录：Android 9 及以下申请一次存储权限，Android 10 起走 MediaStore（不需要权限）。
文件落在「下载」目录里，车机的文件管理器一眼就能看到，拷到 U 盘也好拷。

**换车机的两种走法**：

1. 不同网络：老车机「导出到下载」→ 把文件拷到新车机的「下载」目录 → 新车机「从下载导入」；
2. 同一个 Wi-Fi / 热点：两台车都连上，

   老车机（有歌词的那台）打开「局域网传输」，面板上会显示一个地址，比如
   `http://10.35.199.116:8080`。新车机用**浏览器**打开这个地址，点「下载歌词库」把
   json 存到手机；再在新车机上打开「局域网传输」，把手里的 json 上传上去即可。

   页面上「下载」和「上传」两个方向都有，所以同一套东西既能导出也能导入。
   **服务只在面板开着的时候跑**，关掉面板就停，不会一直挂着端口。

合并规则偏保守：**不会**用更差的版本覆盖更好的版本（导入的句子更多、或本地那份
还没采完，才采用导入的）。所以同一份文件来回传几遍也不会把歌词弄乱。

## 几个关键设计

**为什么必须要有原生代码。** 读别的 App 的 MediaSession（`MediaSessionManager.
getActiveSessions` + `MediaController`）Dart 做不到，而且它要求调用方是一个**已启用的
NotificationListenerService**，所以原生侧既要有 `MediaSessionListenerService`
（一行通知都不处理，只为了拿到权限），也要有 `MediaSessionBridge` 把数据推给 Flutter。

**回放不必等歌词采完。** 一开始只有「整首采齐了」才进回放（`complete && fromStart`），
于是采到一半的稿子很尴尬：重听时界面一直钉在最后那句上不动（车主反馈），越长的歌越明显。
现在只要存下过两句就照着它按时间戳滚，同时继续采缺的（`LyricSessionState.collecting`）——
「回放」和「采集」本来就不冲突，一个负责显示、一个负责补数据：

- 缺口在**后面**（听到一半切走）：接着往后采；
- 缺口在**前面**（打开 App 时已经唱了一半）：从头再放一遍就把开头补上，
  并库按「文本 + 时间」判重，同一句不会变成两句；
- 稿子**收工之后**（采齐了 / 走到过尾巴）就不再回写 —— 那是最准的一版，
  再采只会把时间戳越改越乱。

**协议栈会「停止上报位置」，这时候不能信它。** 真机抓到过：`state=PAUSED`、
`position` 永远等于一个固定值（有时正好是时长）、`speed=0`，而媒体信息里的歌词
两秒一句照常在变。按报的位置算，界面上就会出现：进度条永远是满的、左右时间都是
同一个数、高亮永远停在最后一句、播放按钮显示成「播放」—— 车主截图反馈的就是这个。

兜底规则（`LyricSessionState.derivedPosition` / `playingNow`）：

* **位置不可信**：歌词还在来（[5 秒]内收到过新歌词），但位置已经跑到时长上，或者
  [6 秒]没动过；
* 这时**当前句改成「按歌词文本在稿子里认出来的那一句」**（往上次的位置之后找，
  副歌重复也能跟得上），进度条位置用那一句的时间戳；
* **「在放」改成「播放器说在放，或者歌词刚来过」**，按钮才不会反过来；
* 位置不可信的这段时间**不采集**：每句都会被记成同一个假时间戳，存下来也没法回放。

窗口长度都是构造函数参数，测试里换成假时钟 + 短窗口，不用真的等 6 秒。

**播放位置要自己外推。** 媒体会话只在状态变化时回调，位置不会自己往前走，所以
原生侧起了一个 250ms 的 tick，按 `position + 经过时间 × 倍速` 计算当前位置，歌词才滚得动。

**外推出来的位置会「往回跳」，得压平。** 蓝牙协议栈重推状态时带回来的原始位置，往往
比刚才外推出来的值**少**几百毫秒（真机实测换句那一瞬间：`39269ms → 38516ms → 39483ms`，
退了 753ms）。位置一退，「当前第几句」就跟着退一句、再前进 —— 屏幕上看就是歌词**抽搐
一下**（长句更明显，因为要滚的距离大）。位置在物理上只会往前走，所以 Dart 侧过了
`MonotonicPlaybackClock`：**小于 2 秒的回退按抖动压平**（报上一次的值），**更大的回退
照认**（真拖进度条、换歌重放都靠它）。另外「**掉回开头**（不到 1 秒）永远照认、不当
抖动」—— 采集引擎判「这一遍是从头听起的」看的就是位置有没有掉回开头，不能被压掉。
修完真机复核：170 秒里压平了 126 次回退，「当前第几句」**一次都没倒退过**（修之前
每换一句都退一次），右侧滚动每次正好 +58px（一行）。

**起播时的「真歌手」不能当歌词。** 播放器一开始会往歌手行写真实的歌手名，过一会儿
才换成歌词。所以每首歌**会话开始时那两行的值会作为基线丢掉**，之后的变化才算歌词。
代价是：如果打开 App 时歌词已经在滚，当场那一句收不到，从下一句才开始收。
（歌词在**歌曲名行**时没有这个基线 —— 那一行从头到尾都是歌词，第一句也照收。）

**「同一句连唱两遍」抓不到。** 只在值**变化**时才记，所以连续两句完全一样的歌词
（比如重复的「啊——」）只会记一次。这是这类方案的固有缺陷（网易云也一样），
换来的是全程不需要任何网络请求。

**先按歌名找，找不到再按 key。** 歌名（歌曲名行模式下从歌手行的 `歌曲名 - 歌手` 里切）
基本唯一，且不受播放器报的时长抖动影响；「标题 + 时长」「歌手 + 专辑 + 时长」这两套 key
都带着时长，同一首报 3125 / 3120 秒就会变成两个 key、白采一遍（真机抓到过）。
所以匹配顺序是「歌名 → key → 新采一份」，名字匹配完还要用歌词验一句（见上文）。
key 本身也不能删：重名、歌手行不是那个格式时全靠它兜底。

**「歌曲名 - 歌手」不是歌词。** 网易云把歌词写在歌曲名行时，会把身份信息挪到
歌手行，格式是 `歌曲名 - 歌手`（实测：`ARTIST=Gymnopedie No. 1 - Steve Hackett/John
Hackett`）。换歌时这一行也会变一次，如果照单全收，每首歌都会多出一句垃圾。所以
「歌手名后面的连字符」被当成身份信息直接跳过，不采。

**换歌那一刻的播放位置是上一首的僵尸值。** 蓝牙协议栈会晚几拍才把新歌的播放状态
发过来，于是换歌时读到的位置可能还带着上一首的进度（真机抓到过 5.5s、10.5s）。
这时候如果当场下结论「不是从头听的」，这首歌就会被误标成「缺开头」，明明从头听到
了却要再放一遍才认。所以这种位置先挂着：**掉回开头**就确认是从头听起，**一路往前
跑过 20 秒**才算真的从半路插进来。

**随手跳过的歌不留记录。** 开车时经常听几秒就切下一首（试听、找歌），这种歌没采到
几句，留着只是垃圾 —— 所以**以前没记过**的歌、只往下走了不到 15 秒就被切走，直接
不存。判据是**播放位置往前走了多少**（不是墙上时钟）：暂停着、App 在后台待着的
时间都不算听。库里本来就有稿子的歌不受影响 —— 那是攒下来的东西，不能顺手清掉。

**中途才开始放 → 「缺开头」。** 从半路开始听，前面那几句就是没机会采到。所以会记一个
「开头有没有采到」的标记：没从头采的歌不算「完整」，第二次**从头再放一遍**才会自动补齐
（识别方式：播放位置从几十秒突然回到开头 = 重放了）。在那之前，界面上会提示「缺开头」，
并且宁可继续采、也不拿一份缺了开头的歌词当成完整版同步播放。

## 存哪儿、多大、写多勤

歌词库就是**一个 JSON 文件**（`<应用私有目录>/carlyric/lyrics.json`）。这个格式够用，
但**写盘策略**得讲究 —— 真机上量过（BYD 车机，MediaTek）：

| 规模    | 歌词句数 | 存储文件 | 启动读 + 解析 | 整份编码 | 写盘  |
| ------- | -------- | -------- | ------------- | -------- | ----- |
| 100 首  | 3,233    | 128 KB   | 29 ms         | 21 ms    | 19 ms |
| 300 首  | 10,253   | 402 KB   | 84 ms         | 41 ms    | 25 ms |
| 500 首  | 16,686   | 657 KB   | 140 ms        | 116 ms   | 44 ms |
| 1000 首 | 33,672   | 1.3 MB   | 252 ms        | 148 ms   | 83 ms |

所以几百首完全没压力（文件不到 1MB，启动解析几十毫秒）。真正要小心的是**写的次数**：
早先的写法是「每采到一句就把整个库重写一遍」，500 首时一次 160ms 压在界面线程上、
两三秒来一次 —— 歌词滚动会一顿一顿。现在：

- **合并写入**：连续变化每 8 秒最多整份重写一次（第一次变化仍是 300ms 后写）；
- **该立刻写就立刻写**：一首歌**第一次出现**、**采齐**、删歌、导入；
- **退到后台必写**：熄火 / 切走 / 被系统回收前 `flush()` 一次，不丢句子；
- **原子落盘**：先写 `lyrics.json.tmp` 再改名 —— 写一半被杀掉也不会留下半截 JSON
  （那会让整个歌词库读成空的）。改名是原子操作。

导出的文件是**带缩进**的（人看得懂、方便手改），存储文件是紧凑的 —— 同一份内容，
导出那份大一点无所谓（1000 首约 2.8MB，局域网传几秒），存储那份每分钟要写几次。

真到了**上千首**再说下一步：那时每次整份编码 150ms 就该改成「一首一个文件」了。
现在不做，是因为那会让启动从「读一个文件」变成「开几百个文件」，反而更慢。

## 应用标识与签名

这两样决定了「装到车机上是不是一个新的 App」：

|               | 值                                                           |
| ------------- | ------------------------------------------------------------ |
| 应用显示名    | **LyricCar 歌词**                                            |
| applicationId | `com.homeweb.lyriccar`                                       |
| 签名          | 自己的 `android/app/lyriccar-release.jks`（别名 `lyriccar`） |

于是它和之前的项目（`com.example.stools`）是**两个完全独立的 App**：
applicationId 不同 → 系统不会把安装当成升级，两个 App 可以并存在车机上、互不覆盖；
签名也另起了一套 → 就算以后哪个包用了同名 id，也顶不掉它。

口令不在 `build.gradle.kts` 里，而是在 `android/key.properties`（已被 `.gitignore` 排除，
模板见 `android/key.properties.example`）。没配这个文件时，release 会退回 debug 签名，
只够本地跑通构建，**不要**拿那种包当正式包。

⚠️ **`lyriccar-release.jks` 和那两个口令一定要备份。**
丢了就再也签不出「同一个 App」，以后升级只能让用户先卸载 —— 车机上攒的歌词库会一起没，
所以卸载前记得先「歌词库 → 导出」。

想换成别的包名（比如用自己域名反写），改两个地方即可：
`android/app/build.gradle.kts` 的 `namespace` 与 `applicationId`，
以及 `android/app/src/main/kotlin/` 下的目录名与三个 `.kt` 的 `package` 声明。

这套方案能不能在别的车机上用，只有到了那台车上才知道 —— 而帮忙测试的人未必有电脑、
也未必会接 adb。所以 App 自带一份诊断日志，让他点两下就能把「现场」发回来。

最新的测试安装包和日志都发到 **QQ 粉丝群 829323767** 里，群里直接讨论。

**日志记什么：** App 里所有 `[LyricCar]` 日志（换歌、采集、回放、匹配、写入失败……）
自动落盘，另外每次启动 / 回到前台都会跑一次环境自查：

```
──── 环境自查 ────
App 版本 1.0.1+2
✓ 通知使用权：已授予
监听组件：com.homeweb.lyriccar/com.homeweb.lyriccar.MediaSessionListenerService
──── 系统与会话 ────
【系统】Android 9（SDK 28）
【机型】alps k65v1_64_bsp
【可读会话】4 个
--- 会话 1：com.android.bluetooth ---
  PlaybackState：state=3 position=164581 speed=1.0 actions=54
  元数据 7 项：
    android.media.metadata.ARTIST = 遇见 - 蛋堡
    android.media.metadata.TITLE = 那不会有预兆
    …
```

**让他怎么做（照抄给他）：**

1. 装上 App，按提示开「通知使用权」（左侧面板如果显示「未在播放」，就是没开）；
2. 用车的蓝牙放一首歌，**放半分钟**（让日志里留下播放器真正发出来的东西）；
3. 打开「设置 → 诊断日志」，点「导出到下载」；
4. 把下载目录里的 `lyriccar-log-*.txt` 发回来。

手机和车机在同一个 Wi-Fi 时，第 3 步也可以点「用手机来取」，让他用手机浏览器打开
面板上的地址（页面里第三段就是「下载诊断日志」），文件直接存进手机。

**拿到日志先看这几行**（对应到具体毛病）：

| 日志里的东西 | 说明什么 | 怎么办 |
| --- | --- | --- |
| `✗ 通知使用权：未授予` | 读不到任何别的 App | 只能去系统设置里授，或 adb 一条命令 |
| `【可读会话】0 个` | 权限有了，但系统里没有播放器发布会话 | 车机播放器不发布 MediaSession，这套方案在这台车上用不了 |
| `【可读会话】N 个` 但没有 `com.android.bluetooth` | 放歌走的不是系统蓝牙播放器（比如车机自带音乐 App） | 应用自带的那个会话就行，看它的元数据 |
| 某个会话的 `TITLE/ARTIST/ALBUM` 只有 0~1 个键 | 播放器没开「车载歌词」 | 让他在播放器里打开车载歌词 / 蓝牙歌词 |
| `TITLE` 每两秒变一次 | 歌词写在**歌曲名行** | 「自动判断」能认，或手动选「歌曲名行」 |
| `ARTIST` 每两秒变一次 | 歌词写在**歌手行** | 手动选「歌手行」 |
| `state=2 position=…` 一直不变、但 TITLE 在变 | 协议栈停止上报位置 | 已自动兜底（只回放、不采集），日志里会有「不再报播放位置」 |
| `SDK 23` 等字样 | 顺带确认 Android 版本 | 见下一节 |

日志文件在 App 私有目录 `<应用目录>/carlyric/diagnostics.log`，超过 256 KB 会滚成
`.1`（只留一份旧的），所以不会无限增长。

## 支持的最低 Android 版本

包里声明的是 **`minSdk = 23`（Android 6.0）**，`aapt2 dump badging` 能看到
`minSdkVersion:'23'`。降到 24 以下需要绕一道弯，见下。

**为什么要绕。** Flutter 3.47 的默认 minSdk 是 24，而且 flutter 工具会把
`build.gradle.kts` 里「16~23」这种**字面量**当成「太旧」并自动改回 24
（`flutter_tools` 的 `tooOldMinSdkVersionEqualsMatch`）。所以本仓库把它写成变量：

```kotlin
val lyriccarMinSdk = 23          // 见 build.gradle.kts
...
        minSdk = lyriccarMinSdk
```

**验证到哪一步了（可复现）：**

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| APK 声明的最低版本 | `aapt2 dump badging app-release.apk \| grep sdkVersion` | `minSdkVersion:'23'`、`targetSdkVersion:'36'` |
| 合并后的清单 | `build/app/intermediates/merged_manifests/release/.../AndroidManifest.xml` | `android:minSdkVersion="23"`（说明所有依赖库也都不高于 23） |
| **越级 API 调用**（关键） | `cd android && ./gradlew :app:lintRelease` | `NewApi` **0 条错误** |

最后一条是真凭实据：Android Lint 会逐个检查每个 API 调用，minSdk=23 时任何
API 24+ 的调用都会报 `NewApi` 错误。第一次跑出来 3 条错误，全部在
`LyricTransferChannel` 的 `MediaStore.Downloads` 上 —— 那段其实只在
`Build.VERSION.SDK_INT > P` 时才被调用（用属性当闸门，lint 看不出来），
标上 `@RequiresApi(Q)` 之后就干净了。**现在 0 错误 = 我们自己的 Kotlin 代码里
没有一处会在 Android 6.0 上崩。**

**给 Android 6.0 车上的人测时，日志里重点看：**

* `【系统】… （SDK 23）` —— 确认真的是 6.0；
* `【可读会话】` 后面有没有 `com.android.bluetooth`；
* 点「导出到下载」能不能成功（6.0 走的是老路径：公共目录 + 运行时
  `WRITE_EXTERNAL_STORAGE`，日志里失败会写「导出失败：…」）。

**还要注意的风险（说实话）：**

* `flutter build` 会打一条警告：*support for your project's minimum Android SDK
  version (23) will soon be dropped* —— 24 以下**现在是能用但已进入弃用期**，
  升级 Flutter 大版本时要重新确认；
* 本仓库**没有**在真正的 Android 6.0 车机上跑过（手边的车机是 Android 9）。
  真要上车测，重点看这三件事：**通知使用权能不能授**、
  **能不能读到蓝牙播放器的媒体会话**、**导出能不能写进「下载」目录**；
* Android 6.0 上**导出走的是老路径**：公共目录 `下载/LyricCar/` + 运行时申请
  `WRITE_EXTERNAL_STORAGE`（6.0 正好是运行时权限的第一版）。

- **播放器「罢工」不再让界面假死。** 真机上遇到过车机蓝牙协议栈停止推送播放状态：

  **进度条永远是满的、左右时间一样、高亮停在最后一句、按钮显示成「播放」**

## 局限（先知道比较好）

- 车机自带的蓝牙播放器**不一定**会把自己的播放状态发布成 MediaSession。多数 Android
  车机（尤其是自带播放器是系统应用的那种）会，但这不是 Android 的强制要求 ——
  如果左侧面板始终显示「未在播放」，就是这个原因。装个网易云/QQ 音乐的
  Android 车机版能立刻验证：它们一定会有 MediaSession。
- 采集依赖播放器把歌词写进媒体信息。播放器自己关掉了「车载歌词」，本 App 就无米下锅。
- 一条歌词的时间戳是「收到那次元数据更新时的播放位置」，比原版歌词有一个元数据
  推送延迟（通常几十到几百毫秒），滚动效果以能用为准。
- 「自动判断」要**看它变一次**才能认出歌词写在哪一行，所以一首歌的**头一两句歌词
  第一次听会漏掉**（之后每次听都是完整的）。左边面板能看到它认出来的那一行。
- 「按歌名找」依赖歌手行里的 `歌曲名 - 歌手`。播放器只给纯歌手名时，会退而求其次
  把「切歌后第一眼看到的标题」当真歌名 —— 那一眼如果已经是歌词，这首歌就只能按
  换歌后那套 key 找（效果和以前一样）。
- 半份稿子回放时，**缺开头的部分没法凭空补**：如果这首只采到后半段，从头放一遍之前
  它不会显示前半段的歌词（那几句本来就没采到，界面会提示「开头那段还没采到」）。
  这也是判重靠「文本 + 时间」的代价：同一句歌词在两次播放里报上来的位置差超过
  1.5 秒，就会被当成新的一句（副歌重复唱时也会各记一次，那是本来就想要的）。
- 右侧超长的一句会**自动缩小到装得下**（而不是被切掉后半截）。所以偶尔会看到某一句
  字比旁边小一号 —— 那是它本来就长得放不下。左侧那一格是「系统原始值」的调试位，
  超长时省略号收尾，完整句子看右边。
- 局域网传输需要手机和车机在同一个 Wi-Fi / 热点下，而且传输时**别退出 App** ——
  页面就是 App 自己提供的。地址里的 IP 每个网络都不一样，换网络后重新看一眼面板。
- 车机上 4G 模块的网卡地址（`ccmni*`）也是 10.x，看着像内网但手机连不上 ——
  面板已经把它们过滤掉了，只显示 Wi-Fi / 热点的地址。
